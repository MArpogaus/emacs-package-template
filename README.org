** About The Project

A starting point for an Emacs Lisp package that is ready for MELPA on
day one: the file headers, the checks and the CI workflow are already
in place, so the first commit is about the feature and not about
scaffolding.

Everything here is checked by the same pipeline the other packages use.
Running =make= byte-compiles with warnings as errors, runs =checkdoc=,
=package-lint= and =relint=, and runs the test suite.

** Getting Started

*** Use the Template

Create a repository from this template on GitHub, then rename the
placeholder to the package name.  The name appears in the file names,
in the symbol prefix and in the URLs:

#+begin_src shell
  name=your-package
  git mv my-package.el "$name.el"
  git mv test/my-package-test.el "test/$name-test.el"
  grep -rl my-package . --exclude-dir=.git | xargs sed -i "s/my-package/$name/g"
  grep -rl emacs-package-template . --exclude-dir=.git | \
      xargs sed -i "s/emacs-package-template/$name/g"
  make
#+end_src

Then write the feature, adjust =Package-Requires= to the oldest Emacs
release you support, and list that release first in the CI matrix.

*** File Structure

#+begin_example
  .dir-locals.el                    indentation and fill column for contributors
  .elpaignore                       files MELPA leaves out of the package
  .github/dependabot.yml            weekly action updates, onto dev
  .github/workflows/test.yml        CI, one job per supported Emacs version
  .github/workflows/pre-commit.yml  CI, the hooks over every file
  .github/workflows/release.yml     a release for each pushed tag
  .gitignore
  .pre-commit-config.yaml           the hooks
  COPYING                           GPLv3
  Makefile                          compile, checkdoc, lint, relint, test
  README.org
  my-package.el                     the package
  test/my-package-test.el           ERT suite
  tools/indent.el                   the formatter
#+end_example

** Development

*** Make Targets

| Target     | What it does                                    |
|------------+-------------------------------------------------|
| =compile=  | byte-compile, warnings are errors               |
| =checkdoc= | documentation style, any output fails           |
| =lint=     | package-lint, the rules MELPA applies           |
| =relint=   | the regular expressions and the docstring escapes |
| =test=     | ERT suite                                       |
| =format=   | indent every Lisp file in place                 |
| =clean=    | remove build output and the tool sandbox        |

Plain =make= runs every check in that order, exactly as the CI does;
=format= is not one of them, because it writes.  The =lint= and
=relint= targets install their tools into =.sandbox/=, so a fresh
checkout needs nothing but Emacs and =make=.

*** Hooks

=.pre-commit-config.yaml= runs the same checks before a commit, and the
heavier ones before a push:

#+begin_src shell
  pre-commit install --install-hooks -t pre-commit -t commit-msg -t pre-push
#+end_src

Whitespace, YAML and the commit message come from the usual hook
repositories.  [[https://github.com/MArpogaus/elisp-complexity][elisp-complexity]] scores each function by how much of it a
reader has to hold at once and stops a commit where one function costs
more than 15; it says nothing when everything is under.  The
indentation, =checkdoc= and =relint= run on every commit,
=package-lint= and the suite before a push.

The formatter is =tools/indent.el=, and it gives Lisp the indentation
=indent-region= gives it and nothing more: no form is rewritten and no
line reflowed, so what a reader lined up by hand stays as it is.  It
visits each file rather than reading it, which is how the
=indent-tabs-mode= of =.dir-locals.el= applies rather than the default
of whichever Emacs runs it, and it loads each file first, because a
macro that is not defined looks like a function call and its body would
be lined up as an argument.

The =pre-commit= workflow runs the same hooks over every file, so a
commit made without them is still checked.  Dependabot proposes action
updates weekly against =dev=; the actions are pinned to commit hashes,
which [[https://github.com/suzuki-shunsuke/pinact][pinact]] both writes and verifies.

*** Conventions

- One package prefix for every symbol; private ones use a double dash.
- Every file carries the header block, =;;; Commentary:=, =;;; Code:=,
  a =provide= form and the footer comment.
- Autoload cookies on the entry points only: commands, minor modes and
  variables a user sets before the package is loaded.
- Docstrings end sentences with two spaces, name their arguments in
  upper case and quote symbols as =`symbol'=.
- Commits follow the conventional commit style; work happens on =dev=
  and reaches =main= as a merge commit, which is then tagged.
- A function that costs a reader more than 15 is worth splitting; the
  complexity hook says which one and by how much.
- Code written with an AI assistant carries an =Assisted-by:= line under
  the =Author:= line, which is what MELPA asks for:
  =;; Assisted-by: Claude:claude-opus-5=.

** Publishing on MELPA

1. Tag a release, so MELPA Stable has something to build.
2. Fork [[https://github.com/melpa/melpa][melpa/melpa]] and add =recipes/<package>=:

   #+begin_src emacs-lisp
     (my-package
      :fetcher github
      :repo "MArpogaus/my-package")
   #+end_src

   Add =:branch "main"= when the default branch is not the one to
   package.  The =.elpaignore= file keeps the tests and the CI files
   out; a =:files= specification is not needed.
3. Check the recipe locally in the melpa checkout:

   #+begin_src shell
     make recipes/my-package
     make sandbox INSTALL=my-package
   #+end_src
4. Open the pull request.  The checklist in the template asks for the
   package to be lint-clean, which =make lint= already answers.
